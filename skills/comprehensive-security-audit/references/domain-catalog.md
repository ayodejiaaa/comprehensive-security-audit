# Domain catalog

This is a menu, not a checklist to complete mechanically. Read the "baseline" section as domains almost every audit needs; read the "conditional" section and include whichever entries match signals you actually found in Step 1 recon. If the app has something not listed here (it will, eventually), write a new domain for it using the same shape: business context, scope, attack classes.

## Baseline domains (include in nearly every audit)

### Authentication & session security
Scope: signup, login, logout, password reset/change, email verification, session/token issuance and invalidation, MFA if present, rate limiting on all of the above.
Check: authentication bypass, user enumeration, weak password policy, session fixation/hijacking, improper invalidation on password change or suspension, token entropy and expiry, brute-force/lockout behavior, timing side channels, whether rate limiting fails open when its backing store is unavailable or unconfigured, cookie flags (httpOnly/secure/sameSite), JWT/session claim tampering, OAuth/social login state and redirect handling.

### Authorization / IDOR / BOLA across every resource
Scope: every API route or server action that reads or writes a resource with an owner.
Check: for each resource, does the query scope by the caller's identity (or their relationship to the resource — participant, member, owner) or only by the resource's own id? Test mentally: swap the id for another user's, call another user's action, read another tenant's data. Distinguish "checked in the UI only" from "checked server-side" — only the latter counts as a control. Mass assignment: can a client set fields it shouldn't (role, balance, verification status, ownership) through a generic update endpoint?

### Admin & privilege boundaries
Scope: every admin-only route/page, role-check helper, impersonation or "view as" features, privilege escalation paths (self-registration, profile updates, any endpoint that ever writes a role/permission field).
Check: is the admin check the *first* operation in every handler, for every HTTP verb, not just GET? Is it server-side and DB-backed (not just a cached claim)? If impersonation exists: can it chain, target other admins, or be used to move money/change security-sensitive settings with no audit trail? Is there a durable, queryable audit log for admin actions, or only ephemeral logging?

### Data exposure, input validation, injection, XSS
Scope: every response shape (does an endpoint return more fields than the caller needs — internal ids, other users' data, secrets baked into a `select *`?), every place user text is stored and later rendered, every raw-SQL or templated-query usage, every file upload.
Check: SQL/NoSQL injection (parameterization, not just escaping), XSS (especially indirect ones — JSON embedded in `<script>` tags via `dangerouslySetInnerHTML`/similar, which is a classic and easy-to-miss `</script>` breakout since naive JSON serialization doesn't escape `<`), HTML sanitizer configuration (allowed tags/attributes/schemes), stored vs reflected, CSRF where cookies are used for auth, file upload validation (is MIME/type checked by content or just by client-declared header?), path traversal, SSRF via any user- or third-party-controlled URL the server fetches.

### Configuration, secrets, dependencies, deployment
Scope: env var usage, `.gitignore` coverage, git history for leaked secrets, HTTP security headers, CORS, dependency advisories, any "test mode"/"simulated"/"debug" flag that changes production behavior, deployment/preview environment isolation from production data.
Check: `npm audit` (or equivalent) for direct vs transitive, prod vs dev-only severity; secrets never committed (check history, not just the current tree); security headers (CSP — note whether `unsafe-inline` is set and what that means given the app's actual inline-script usage; X-Frame-Options/frame-ancestors; HSTS; nosniff; Referrer-Policy); any environment-gated dangerous mode (does it fail closed by default, or does an unset/misconfigured variable silently enable it?); whether preview/staging environments share production secrets or data.

## Conditional domains (include when the signal is present)

| Signal from Step 1 | Add this domain | Core checks |
|---|---|---|
| Any money movement — payments, wallet, credits, invoicing | **Financial flow(s) — split "money in" (charging, top-ups, webhooks) from "money out" (refunds, payouts, releases) if both exist** | Webhook signature verification and idempotency (a check-then-act pattern instead of an atomic conditional update is the single most common real bug here — look for it explicitly); double-spend/double-credit under concurrent or replayed requests; amount/currency validated server-side, never trusted from the client; ledger integrity (append-only in practice, not just by convention — are there DB constraints/triggers, or could any code path rewrite history?); refund/void paths idempotent and not exploitable for double benefit; commission/fee math computed server-side |
| Escrow, marketplace, "protected payments", holds/releases | **Release & dispute logic** | Every release path (approval, timeout/silence auto-release, admin override) must be mutually exclusive and atomic under a lock — check for double-release across these paths; release never exceeds what's held; refund-then-release or release-during-dispute should be structurally impossible, not just discouraged; admin dispute resolution arithmetic validated server-side |
| Two-sided marketplace, bidding, matching, auctions | **Matching/bidding state machine** | State transitions enforced by atomic conditional updates (`WHERE status = expected`), not read-then-write; competing bids/offers never disclosed to the wrong party; caps and limits (slots, budgets, free-tier allowances) enforced under concurrency, not just checked-then-incremented; self-dealing (can one person act as both sides of a transaction via a second account?) |
| In-app messaging between otherwise-untrusted users | **Chat/messaging authorization & content controls** | Only participants can read/write a thread (check the actual join/where clause, not just "logged in"); any content-scrubbing/redaction rule (e.g. hiding contact info) is applied server-side at write time and is realistically resistant to being defeated by splitting content across messages, alternate encodings, or homoglyphs — treat this as a best-effort deterrent and say so rather than certifying it's unbeatable; rate limiting on sends; rendering as text, not raw HTML |
| Identity verification / KYC, document or ID checks | **Identity & PII handling** | Sensitive identifiers (SSN/NIN/passport/etc.) encrypted at rest with authenticated encryption and a key that fails closed if unset; verification logic actually binds the claimed identity to the account (not just "a name string matches" — check how weak that match is); any endpoint that echoes back a third party's PII on a mismatch is an oracle — flag it even if "expected" behavior; rate limiting on paid/costly verification calls; machine-to-machine endpoints for partner integrations use strong auth and return the minimum necessary data |
| Reviews, ratings, reputation | **Reputation integrity** | Eligibility to review is tied to a real, costly interaction, not a trivially cheap one; double-blind reveal timing can't be gamed by waiting for the other side then retaliating; one review per relevant pair/interaction; rating aggregates only ever include reviews meant to be public |
| File/media uploads | **Upload handling** | Content-type verified by sniffing, not just trusting the client header; size limits enforced server-side; storage is on a separate origin/domain from the app (so an uploaded file can't execute as same-origin script); filenames server-generated, not attacker-controlled; old files cleaned up or at least not silently orphaned in a way that matters |
| Third-party OAuth / webhook integrations | **Third-party integration security** | OAuth state is single-use, bound to the session, and expires; webhook signatures verified in constant time and fail closed when the secret is unset; replay windows bounded; account-linking can't be hijacked to attach one person's identity/credentials to another's account |
| Multi-tenant SaaS | **Tenant isolation** | Every query scoped by tenant id, not just resource id; background jobs and cross-tenant admin tooling scoped correctly; shared caches/queues don't leak across tenants |
| Cron/scheduled jobs, background workers | **Job security & idempotency** | Job-triggering endpoints authenticated (bearer secret, signed request) and fail closed if the secret is unset; overlapping/duplicate runs can't double-process (claim-based locking, not just "it's hourly so it's fine") |
| App serves or is marketed to Nigerian users (`.ng` domain, ₦/NGN currency, +234 numbers, Nigerian business address/footer, Nigeria-targeted copy) and collects any personal data at signup, via analytics, or via email | **Nigeria Data Protection Act (NDPA) compliance** | This domain is regulatory-exposure, not a classic vulnerability class — frame findings as compliance gaps with a cited NDPA section and the statutory fine band, not as "attacker scenarios." Check specifically: (1) any signup/onboarding flow that collects personal data with no age gate or parental/guardian consent path — NDPA s.31, processing a minor's data without consent; (2) third-party assets loaded from foreign origins that transmit visitor IPs or other personal data without a documented transfer safeguard — the canonical case is fonts/analytics/CDN scripts pulled live from a non-Nigerian domain (e.g. `fonts.googleapis.com`) instead of self-hosted — NDPA s.41 cross-border transfer; (3) session-replay/heatmap tools (Hotjar, Microsoft Clarity, FullStory, etc.) wired up and recording by default, especially if they can capture keystrokes in password/payment fields, with no consent banner gating them; (4) any marketing/broadcast email (launch announcements, waitlist mail, newsletters) sent without a working unsubscribe mechanism and a physical/postal address in the footer; (5) whether a lawful basis is documented anywhere for each category of personal data collected — a privacy-policy page existing is not the same as a basis being recorded per processing activity. Don't invent this domain for an app with no Nigeria signal — it's conditional, not baseline. |

If the app has a domain not listed here, build one: name it, write 2-3 sentences of business context, list the exact files in scope, and derive attack classes from what could plausibly go wrong given what that subsystem does (who benefits from abusing it, and how).
